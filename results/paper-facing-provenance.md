**Reading of your list.** Covered by the transfer table: `e0-numinstructions` (185), `e1-vf-chain` (18), `e1-hf-batch` (16), `e1-preproc` (20) and `e2-chain` (7) = 5 binaries, 246 kernels, all identical (confirmed). Built at c8fcbe8 directly: `e0-npp-after45` (and the CPU-time one), E9, E16, E6, E3 repeat, E4 (its raw CSVs have `# fkl: c8fcbe8` and `# repo: 51fa9e6`; only the derived `e4_summary.csv` / `e4_speedups.csv` have no header), E11 (compile only), the RPP and the repeated numinstructions rows of the AMD side. **Correction: E2 runs 3 and 4 are NOT built at c8fcbe8.** The FKL chain binary is the same frozen 38c4f32 binary in all four runs (the headers of `e2_fkl_chain.csv`); the c8fcbe8 line of `e2_chain.csv` comes from the Python script's checkout. The paper's E2 numbers are `e2_compact.csv`, the median of runs 2, 3, 4.

**Scope of the sentence "every kernel is SASS-identical at the pin".** It holds, with registers included, for the kernels of the binaries behind the NVIDIA E0 numbers (instructions per operation: 185 kernels) and E1 (54) and E2 (7), i.e. the five binaries above (246 kernels; the transfer table has 20 binaries and 1,116 kernels in all, the rest not paper-facing now). It says nothing about the AMD results (no transfer comparison is known to me; the AMD agent's own comparison of the library-checks PR is a different question), about E3 (compile times), or about E4, E6, E9, E16, the NPP re-runs, which were built at c8fcbe8 and need no transfer.

**`-dirty`.** In the headers written by the C++ build info (`fklb_build_info`, used by E4, E6, E9, E16, the NPP programs and the AMD binaries) `-dirty` means that a tracked file in `common cmake fkl-self opencv-cuda npp external CMakeLists.txt CMakePresets.json` had uncommitted changes when the binary was built (results, scripts and logs do not count); the commit named is then the HEAD at that moment, not necessarily the exact sources. Affected rows: E16 (c588536, 35ebfd8), E6 (91dfcdd, de47e88), the AMD `latency_hiding_without_spin_same_day` run (its README says why). In the headers written by the Python scripts (E2 `e2_chain.csv`, E3) `-dirty` counts any tracked file, and for the E3 repeat the README names the one file: `results/rtx4090/e0-run.log`. I have not reconstructed what differed in the C++ cases.
