# Host path of ONE batched call, paper state against the current pins: candidates for the CPU-time change (written 2026-11-06; read from git, nothing built at the paper state, no cause claimed)

Paper state: cvGPUSpeedup 002f0f1d (branch 169-add-cuda-graphs-to-some-benchmarks, 2025-07-09; its fkl = 1f33224 = Beta-0.1.8, 2025-05-22), FastNPP 72ddf8a (2025-07-08). Current: cvGS 6d26c65, FastNPP a1b5e245, FKL c8fcbe8.
The timed call (the same source in both states, `benchmarks/benchmark_CPU_OpenCV_vs_cvGS.cu`, lines ~110-117 at 002f0f1d): `cvGS::executeOperations(cv_stream, cvGS::resize<CV_TYPE_I, cv::INTER_LINEAR, BATCH>(crops, up, BATCH), cvGS::cvtColor<..>(), multiply, subtract, divide, cvGS::split<CV_TYPE_O>(d_tensor_output, up))`. The output is ONE tensor (a single write descriptor, no per-crop write cost); the per-crop work is all on the READ side: `resize` over the array of BATCH crops.

## What a crop costs in bytes (measured now, read at the paper state)
- RawPtr<_2D, uchar3> 24 bytes (data pointer 8 + PtrDims<_2D> {width, height, pitch} 12, padded); read IOp 24; the resize IOp (its OperationData) 48; `Size` 8. In the paper state the 48 are `ResizeReadParams` 24 (dstSize 8, src_conv_factors 8, the interpolation parameter Size 8) + the back IOp's RawPtr 24.
- NOW, measured with a host-only program at the current pins (`sizeof`, no CUDA call; scratch/sizeof-cur): BatchRead IOp 6,848 bytes at batch 142 = 48.2 bytes per crop (the kernel parameter of the read), opData element 48, resize IOp 48, array of read IOps 24 per crop, array of Size 8 per crop.
- PAPER STATE, by reading `resize.cuh:44-58`, `ptr_nd.cuh:39-43`, `batch_operations.cuh:84-98` (BatchReadParams: `OperationData<Operation> opData[BATCH]`): also 48 bytes per crop. **The size of the kernel parameter per crop did not change**, so the bytes the driver copies into the launch are not what differs (the driver and runtime of 2025, CUDA 12.x, are not here).
- Bytes moved per crop on the host, counting every pass (construction, copy into arrays, copy into the params, copy by the executor, the launch): NOW about 500 (build_batch of the reads 24 zeroed + 24 written; of the resize IOps 48 + 48; Size 8; BatchRead: params zeroed 48 + element assigned 48 + `BatchReadType::build(paramsStore)` 48 + return; executor `fuse_back` 48 + `tuple_cat` 48; launch 48); at 20 to 30 GB/s that is 15 to 25 ns, **which is the measured marginal cost now (0.020 microseconds per crop between batch 62 and 152)**. PAPER STATE by the same count: about the same number of passes (build_batch result 24, resize array 48 + its elements 48, `static_cast<OperationData>` temporary 48 + array element 48, `get<0>(iOps...)` 48, launch 48): about 400. The copy volume does not explain a factor of 5 (0.10 to 0.14 microseconds per crop).

## Corrections of what was reported before
- `results/rtx4090/e0-cpu-time-history/README.md` says the cvGS batched-resize wrapper is 'the same code from Alpha-0.0.20 to 6d26c65 (enum renames only)'. That is wrong for its last statement: until 2025-09-18 (cvGPUSpeedup `e9958c5` 'Some more fixes') the wrapper ended with `Resize::build_batch(readOP, sizeArr)` and `fk::BatchRead<NPtr, fk::CONDITIONAL_WITH_DEFAULT>::build(resizeDFs, usedPlanes, backgroundValue)` (002f0f1d:239-245); now it ends with `fk::Resize<IType, AR>::build(usedPlanes, backgroundValue, readOP, sizeArr)` (6d26c65). The front part (`gpuMat2RawPtr2D_arr`, `PixelReadOp::build_batch(fk_input)`, `make_set_std_array`) is unchanged. The cvGS `executeOperations` also changed on the same occasion (`fk::Stream fk_stream(cu_stream)` per call, an explicit `TransformDPP<defaultParArch, TFOPT>`).

## TEST A: reading of the 2025 figure by the coordinator, accuracy about +-1 to +-2, NOT data (added 2026-11-06)
The coordinator rendered the 2025 CPU-time figure (`old-figures/test_cpu_batchresize_x_split3D.pdf`, 300 dpi) and read its left end (accuracy about +-1 at batch 2, +-2 elsewhere). Speedups at batches 2 / 12 / 22 / 32 / 42:
- 2025, read from the figure: cvGS against OpenCV-CUDA about 12 / 56 / 84 / 100.5 / 112; FastNPP against NPP about 12 / 43 / 60 / 70 / 74.5.
- 2026, from the CSVs: cvGS 14.3 / 72.6 / 125.6 / 164.5 / 207.6; FastNPP (run 1 after #45) 14.7 / 57.7 / 104.9 / 139.3 / 163.5.
- 2026 baseline host times (microseconds) at the same batches: OpenCV-CUDA 25.9 / 158.8 / 286.3 / 407.3 / 531.8; NPP 27.5 / 155.7 / 281.5 / 410.7 / 539.3.
IF the baselines were the same in 2025, the implied 2025 fused host times (baseline / speedup) are, in microseconds: cvGS 2.16 / 2.84 / 3.41 / 4.05 / 4.75 (2026: 1.82 / 2.25 / 2.30 / 2.52 / 2.58); FastNPP 2.29 / 3.62 / 4.69 / 5.87 / 7.24 (2026: 1.90 / 2.75 / 2.73 / 2.99 / 3.31).
The constant at batch 2 differs by about 15 to 20 percent (within what a reading of 12 +-1 allows); the slope between batch 2 and 42 is about 3.4 to 3.5 times larger in 2025: cvGS 0.065 against 0.019 microseconds per crop, FastNPP 0.124 against 0.035. So the per-crop part of the fused host time is what changed, not a slower launch constant. This favours candidate 7 (host flags of the header-only per-crop code) or the differences of form in candidates 1 and 3 over a toolchain-wide slowdown; it is not a proof (it holds only if the 2025 baseline times per batch were the 2026 ones).

## TEST B: the host time of building the descriptors of the timed calls, against the host flags (current pins, CPU only, no CUDA call; 2026-11-06 17:04 to 17:06)
`test-B/hostbench.cu` builds, in a loop, the expressions of the two timed calls without launching anything: cvGS `resize<CV_8UC3, INTER_LINEAR, B>(crops, up, B)` + `cvtColor` + `multiply` + `subtract` + `divide` + `split(tensor)`; FastNPP `ResizeBatch_8u32f_C3R_Advanced_Ctx` (body copied from `fast_npp.h`, its one `cudaGetDevice` call replaced by a constant) + `SwapChannels` + `MulC` + `SubC` + `DivC` + `CopyBatch_32f_C3P3R_Ctx<B>` (the per-crop WRITE descriptor of FastNPP). Pins: cvGS 6d26c65, FastNPP a1b5e245, FKL c8fcbe8; B = 2, 12, 42, 142. Built with six host flag sets through nvcc, run pinned to cores 0-3,16-19 with `CUDA_VISIBLE_DEVICES` empty (a CUDA call would fail; none did), three rounds, load before 1.03 0.39 0.93 and after 1.09 0.53 0.94 (`test-B/testB_results.csv`, `build-and-run.sh`, `summarise.py`, full tables in `testB_summary.md`).
**What nvcc passes to g++ with an EMPTY CMAKE_BUILD_TYPE** (the 2025 cvGS CMake sets no default build type): a CMake configure of the current cvGPUSpeedup with an empty build type gives `CUDA_FLAGS = -std=c++17 -arch=native --threads 0 -rdc=false -split-compile=0 -lineinfo` (no `-O`, no `-DNDEBUG`; the `-march=native -mtune=native` of `archflags.cmake` is only for CXX-language sources, not for the `.cu` files); the `nvcc --dryrun` of that compile shows the host step as `gcc -std=c++17 -D__CUDA_ARCH_LIST__=890 -c -x c++ -DCUDA_DOUBLE_MATH_FUNCTIONS -Wno-psabi ... -m64 <cudafe output>`: **no optimisation flag at all, i.e. gcc -O0, and assertions on (no NDEBUG)**. The flag set `emptybuildtype` of the program is exactly that; `o3ndebug` is what CMake's Release gives (and what fkl-benchmarks uses: it forces Release when no build type is given, `cmake/fklb_targets.cmake:18`).
Result (microseconds per call, median of the three rounds; slope = ns per crop between B = 2 and B = 42, the range of the 2025 reading in Test A):
| host flags | cvGS B=2 | B=142 | slope | FastNPP B=2 | B=142 | slope |
|---|---:|---:|---:|---:|---:|---:|
| -O3 -DNDEBUG (Release) | 0.042 | 2.161 | 16.3 | 0.071 | 2.859 | 21.9 |
| -O2 -DNDEBUG | 0.052 | 1.802 | 13.9 | 0.077 | 3.295 | 25.0 |
| -O1 -DNDEBUG | 0.039 | 1.986 | 15.1 | 0.069 | 3.268 | 24.5 |
| -O0 -DNDEBUG | 0.306 | 8.113 | 57.4 | 0.411 | 16.472 | 118.8 |
| -O3, no NDEBUG | 0.041 | 2.173 | 16.5 | 0.075 | 2.888 | 21.9 |
| **empty build type** (no -O, no NDEBUG) | 0.295 | 7.993 | **58.9** | 0.411 | 16.572 | **118.2** |
So at -O1 and above the construction costs 14 to 25 ns per crop; at -O0, with or without NDEBUG, 57 to 59 ns per crop for cvGS and 118 to 119 for FastNPP: **3.6 times (cvGS) and 5.4 times (FastNPP) more per crop than Release**, a constant (B = 2) larger by 0.15 to 0.35 microseconds. NDEBUG alone changes nothing at -O3 (16.5 against 16.3). The largest spread of the three rounds is 0 to 3 % at -O0 and 1 to 28 % at -O1 to -O3 (values of 40 to 100 ns at B = 2).
Against the real harnesses (executor and launch included, Release, 2026) and the 2025 reading of Test A (slope between batch 2 and 42): cvGS 2026 0.019 us per crop, 2025 reading 0.065; FastNPP 2026 0.035, 2025 reading 0.124. The construction alone, empty build type: 0.059 and 0.118; Release: 0.016 and 0.022. The ratio 2025 / 2026 of the real slopes (3.4 and 3.5) is the ratio of the empty build type to Release of the construction (3.6 and 5.4), and the absolute slope of the empty build type plus the executor and launch part of the Release slope (0.003 for cvGS, 0.013 for FastNPP) is 0.062 and 0.131 us per crop, against 0.065 and 0.124 read. At B = 142 the construction at the empty build type exceeds the Release one by 5.8 us (cvGS) and 13.7 us (FastNPP) against the excess implied by the 2025 plateaus of 10.5 and 13.4 us; NPP with the CPU part at batch 150: 14.3 us (Test B, (118.2 - 21.9) ns x 150) against 14.1 us implied.
**What this shows and what not.** It shows that the harness built with the flags an empty CMAKE_BUILD_TYPE gives (host code at -O0, assertions on) has a per-crop host cost of the size that the 2025 figures imply, with this library code (c8fcbe8); it is consistent with candidate 7 and does not by itself prove that the 2025 binaries were built that way (the 2025 library code differs: the fold expressions of candidates 1 and 3 behave differently at -O0, and the executor and launch part at -O0 was not measured). What would settle it: how the 2025 benchmarks were built (the CMake command or the cache, `CMAKE_BUILD_TYPE`), or Test C (the real harnesses built with Release, an empty build type and Debug, at the current pins, alternating, one window of about 1 to 2 minutes).

## What would separate the candidates (proposals only, nothing run)
1. No build: the 2025 figure at its LEFT end. The fused host time is (constant) + (slope x batch). In 2026 the constant is about 1.5 microseconds (batch 2: cvGS 1.8) and the slope 0.020. If the 2025 curve at batch 2 and 12 is read off the PDF, the speedup there says whether the 2025 constant was also larger (a different toolchain or CPU: everything slower) or only the slope (per-crop host code). Prediction of 'only the slope x5': speedup at batch 2 about 14, at 12 about 70 for the constant 1.5; a plateau of 120 from batch 62 needs the constant to stay below ~3 microseconds.
2. At the CURRENT pins, CPU only, no GPU: the per-crop construction chain of the timed call (`cvGS::resize<...>(crops, up, B)` and the rest) in a host-only loop, built at -O0, -O1, -O2 and -O3: gives the slope per crop as a function of the optimisation level on this machine (a compile of one small program; no CUDA call; a second or two of CPU). If the -O0 slope is near 0.1 microseconds per crop, candidate 7 is confirmed as a possible cause of the shape; if not, it is excluded.
3. At the current pins, with the GPU (a window of about 1 minute): the real harness `benchmark_CPU_OpenCV_vs_cvGS_cu` built Release and -O0 (and -O1), the three alternating: the fused host time and the speedup per batch size. This tests the same hypothesis on the real number.
