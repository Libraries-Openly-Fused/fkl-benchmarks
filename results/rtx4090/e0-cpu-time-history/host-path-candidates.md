# Host path of ONE batched call, paper state against the current pins: candidates for the CPU-time change (written 2026-11-06; read from git, nothing built at the paper state, no cause claimed)

Paper state: cvGPUSpeedup 002f0f1d (branch 169-add-cuda-graphs-to-some-benchmarks, 2025-07-09; its fkl = 1f33224 = Beta-0.1.8, 2025-05-22), FastNPP 72ddf8a (2025-07-08). Current: cvGS 6d26c65, FastNPP a1b5e245, FKL c8fcbe8.
The timed call (the same source in both states, `benchmarks/benchmark_CPU_OpenCV_vs_cvGS.cu`, lines ~110-117 at 002f0f1d): `cvGS::executeOperations(cv_stream, cvGS::resize<CV_TYPE_I, cv::INTER_LINEAR, BATCH>(crops, up, BATCH), cvGS::cvtColor<..>(), multiply, subtract, divide, cvGS::split<CV_TYPE_O>(d_tensor_output, up))`. The output is ONE tensor (a single write descriptor, no per-crop write cost); the per-crop work is all on the READ side: `resize` over the array of BATCH crops.

## What a crop costs in bytes (measured now, read at the paper state)
- RawPtr<_2D, uchar3> 24 bytes (data pointer 8 + PtrDims<_2D> {width, height, pitch} 12, padded); read IOp 24; resize IOp = its OperationData 48 (ResizeParams {Size dstSize 8, float2 src_conv_factors 8} + the back IOp's RawPtr 24, + the interpolation Size 8 in the paper state: ResizeReadParams 24 + RawPtr 24 = 48); `Size` 8.
- NOW, measured with a host-only program at the current pins (`sizeof`, no CUDA call; scratch/sizeof-cur): BatchRead IOp 6,848 bytes at batch 142 = 48.2 bytes per crop (the kernel parameter of the read), opData element 48, resize IOp 48, array of read IOps 24 per crop, array of Size 8 per crop.
- PAPER STATE, by reading `resize.cuh:44-58`, `ptr_nd.cuh:39-43`, `batch_operations.cuh:47-53`: also 48 bytes per crop. **The size of the kernel parameter per crop did not change**, so the bytes the driver copies into the launch are not what differs (the driver and runtime of 2025, CUDA 12.x, are not here).
- Bytes moved per crop on the host, counting every pass (construction, copy into arrays, copy into the params, copy by the executor, the launch): NOW about 500 (build_batch of the reads 24 zeroed + 24 written; of the resize IOps 48 + 48; Size 8; BatchRead: params zeroed 48 + element assigned 48 + `BatchReadType::build(paramsStore)` 48 + return; executor `fuse_back` 48 + `tuple_cat` 48; launch 48); at 20 to 30 GB/s that is 15 to 25 ns, **which is the measured marginal cost now (0.020 microseconds per crop between batch 62 and 152)**. PAPER STATE by the same count: about the same number of passes (build_batch result 24, resize array 48 + its elements 48, `static_cast<OperationData>` temporary 48 + array element 48, `get<0>(iOps...)` 48, launch 48): about 400. The copy volume does not explain a factor of 5 (0.10 to 0.14 microseconds per crop).

## Corrections of what was reported before
- `results/rtx4090/e0-cpu-time-history/README.md` says the cvGS batched-resize wrapper is 'the same code from Alpha-0.0.20 to 6d26c65 (enum renames only)'. That is wrong for its last statement: until 2025-09-18 (cvGPUSpeedup `e9958c5` 'Some more fixes') the wrapper ended with `Resize::build_batch(readOP, sizeArr)` and `fk::BatchRead<NPtr, fk::CONDITIONAL_WITH_DEFAULT>::build(resizeDFs, usedPlanes, backgroundValue)` (002f0f1d:239-245); now it ends with `fk::Resize<IType, AR>::build(usedPlanes, backgroundValue, readOP, sizeArr)` (6d26c65). The front part (`gpuMat2RawPtr2D_arr`, `PixelReadOp::build_batch(fk_input)`, `make_set_std_array`) is unchanged. The cvGS `executeOperations` also changed on the same occasion (`fk::Stream fk_stream(cu_stream)` per call, an explicit `TransformDPP<defaultParArch, TFOPT>`).

## What would separate the candidates (proposals only, nothing run)
1. No build: the 2025 figure at its LEFT end. The fused host time is (constant) + (slope x batch). In 2026 the constant is about 1.5 microseconds (batch 2: cvGS 1.8) and the slope 0.020. If the 2025 curve at batch 2 and 12 is read off the PDF, the speedup there says whether the 2025 constant was also larger (a different toolchain or CPU: everything slower) or only the slope (per-crop host code). Prediction of 'only the slope x5': speedup at batch 2 about 14, at 12 about 70 for the constant 1.5; a plateau of 120 from batch 62 needs the constant to stay below ~3 microseconds.
2. At the CURRENT pins, CPU only, no GPU: the per-crop construction chain of the timed call (`cvGS::resize<...>(crops, up, B)` and the rest) in a host-only loop, built at -O0, -O1, -O2 and -O3: gives the slope per crop as a function of the optimisation level on this machine (a compile of one small program; no CUDA call; a second or two of CPU). If the -O0 slope is near 0.1 microseconds per crop, candidate 7 is confirmed as a possible cause of the shape; if not, it is excluded.
3. At the current pins, with the GPU (a window of about 1 minute): the real harness `benchmark_CPU_OpenCV_vs_cvGS_cu` built Release and -O0 (and -O1), the three alternating: the fused host time and the speedup per batch size. This tests the same hypothesis on the real number.
4. Needs Oscar's exception (not requested by me): the old pairs.
