# E3 results (compile only, RTX 4090 machine, nvcc 13.4.92, sm_89, one pinned core per compile)

- `e3_table.md`, `e3_table_chains.csv`, `e3_table_trees.csv`, `e3_table_staticloop.csv`: the tables, generated by `scripts/e3_table.py` from the CSVs below and `../e3-kernel-time/`.
  `param_space_bytes` is the kernel parameter space that ptxas checks against 32,764 B (0x7ffc), computed from the PTX layout of the parameters; ptxas' `cmem[0]` figure
  (`cmem0_bytes_ptxas`) is not that number (it includes reserved bytes).
- Memory: every `*_mb` column of the CSVs and every `peak RSS` figure in this file is MiB (GNU time reports KiB and the scripts divide by 1024); `GiB` = MiB / 1024. Earlier versions of this file wrote GB for MiB / 1000 (13,433 MiB as 13.4 GB); the exact readings are 13.1 GiB or 14.1 GB (10^9 bytes).
- `e3_compile.csv` (variants A and B, current tree, first sweep), `e3_compile_B.csv` (variant B, to the first failure), `e3_compile_A_knee*.csv` (the knee of variant A, N = 1,005 to 1,300),
  `e3_limit_B_384[78].csv` (variant B at N = 3,847 and 3,848), `e3_patched_{A,B}.csv` (the include tree with get_arg without the tuple, a copy in the scratchpad),
  `e3_getarg_pr_A.csv` (the include tree of the local branch LTS-C++17-get-arg-no-tuple), `e3_trees_*.csv`, `e3_limit_{coarse,fine}_*.csv` (fold versus recursion, first failing N),
  `e3_staticloop_mul_add1.csv` (cvGS mul_add1, 2 to 19,902 operations). `*.log`: the console output of each sweep.
- `repro/`: the minimal reproducers without FKL (`fkl-self/compiletime/repro/param_cliff.py`): `param_cliff.csv` has one row per kernel: PTX counts (`ld.param`, `cvta.param`, `st.local`, local depot bytes) and
  cubin figures (registers, spill bytes, STL/LDL). Only the rows `getarg / library / K=1500 and 3000` have more than 20 registers (255).

## The limits found (current tree)

- Variant A (float, 4 B per operation): 17 registers / 0 spills up to N = 1,023, 255 registers from N = 1,024 (cause: `fk::get_arg`, see `fkl-self/compiletime/README.md`); N = 4,000 compiles in 675 s (13,613 MiB = 13.3 GiB);
  N = 6,000 did not finish within 3,600 s. With the fix: 17 registers at every N, N = 4,000 in 697 s (13,429 MiB = 13.1 GiB), N = 6,000 did not finish within 5,400 s. Parameter space limit (predicted, not reached): N = 8,177.
- Variant B (float3 / int3, 12 B per parameterised operation): ok to N = 3,847 (731 s, 12,820 MiB = 12.5 GiB, parameter space 32,752 B); N = 3,848 (32,768 B by the layout model) fails with a ptxas error (exit 255; the sweep CSV keeps only the truncated first line); the full message was captured at N = 4,000
  (`ptxas_error_B_4000.txt`): `Entry function ... uses too much parameter space (0x8508 bytes, 0x7ffc max)`. The layout model reproduces the 0x8508 exactly; the N = 3,848 failure was predicted by it and confirmed by a compile.
- Older trees: 1f33224 first fails at N = 248, 07b2cb3^ and 07b2cb3 at N = 245: `cannot deduce the return type of function "fk::get<Index, ...>"` at parameter_pack_utils.h(34).

## N = 4,000 with the fix: two compiles, and why they differ (2026-10-30)

The distinct-operations chain at N = 4,000 (variant A) was compiled once with the get_arg change from the PR tree and once from the copy of the pin with the same one-function change, and once without the change. One core, `--threads 1`, the flags and the generated translation unit of the top of this file; the three CSV headers record the include directory and the timeout. None of the three was made in a quiet window: the machine was running other compile sweeps, listed below from `../e0-load-audit/load_events.csv` (my own record of what ran; the load logger of `scripts/load_logger.py` did not exist yet on 2026-10-30).

| compile | file | tree and include directory | core | window | nvcc wall (s) | peak RSS (MiB) | cudafe++ / cicc / ptxas / host g++ / other (s) | other compile jobs while it ran |
|---|---|---|---|---|---|---|---|---|
| with the change, PR tree | `cubin-sizes/e3_cubin_A.csv` | `worktrees/fkl-getarg/include`: PR #417 branch, head a8a74ea on LTS-C++17 d776713 | 14 | 17:50:31 to 18:00:26 | 595.2 | 13,433 | 0.90 / 439.5 / 12.1 / 140.8 / 1.8 | none for most of it: one direct nvcc on core 13 (same CCD) for 131 s, builds on cores 4 to 7 (the other CCD) for 134 s |
| with the change, copy of the pin | `e3_patched_A.csv` | copy of the pin 38c4f32 with the same one-function change (scratchpad `fkl-patched/include`) | 14 | 12:07:37 to 12:19:13 | 696.6 | 13,429 | 1.03 / 492.9 / 14.0 / 186.5 / 1.9 | four other compile sweeps on the same CCD (cores 8, 13, 15 and one unpinned), 677 to 696 s of its 696 s |

Reading. The two compiles with the change are the same code (the only differences between the PR tree and the copy of the pin are comments and one `static_assert` message, and the normalised SASS is identical, see the tree check above) and differ by 17 % in wall time: 595.2 s with about one other compile job on its CCD, 696.6 s with four. The difference is in the phases that move a lot of memory: cicc +12 % (439.5 to 492.9 s), host g++ +32 % (140.8 to 186.5 s), ptxas +16 % (12.1 to 14.0 s). The peak compiler memory does not depend on the load (13,433 and 13,429 MiB). The compile without the change took 674.5 s with one other job for two thirds of the time, between the two. The differences between these three compiles at N = 4,000 are therefore mostly the load, not the tree.
Other evidence that the compile time depends on the other jobs: the same PR tree at N = 1,000 took 22.78 s in `cubin-sizes/e3_cubin_A.csv` (17:48, nothing else compiling) and 24.53 to 25.62 s in `e3_getarg_pr_A.csv` (three compiles, four other sweeps running), +8 to +12 %; the pinned tree c8fcbe8 took 22.77 s on 2026-10-31 on an otherwise idle machine (`tree-check/`). Repetitions of the same code under the same conditions agree to 1.3 % (N = 2,000 with the change: 99.09 to 100.37 s in five compiles; without it: 106.95 to 108.36 s in five, `compile-times-1-100-500-2000/`).
A statement the numbers support: at N = 4,000 the compile takes about 600 s when nothing else compiles and up to about 700 s when four other compiles share the CPU; it needs 13.1 GiB (13,433 and 13,429 MiB) of memory in both cases.

## Controlled repeat at the final pin (2026-11-02): `repeat-c8fcbe8/`

67 compiles in one window on the idle machine (13:00:00 to 13:58:42), `external/fkl` at c8fcbe8: the distinct-operations chain at N = 1, 100, 500, 1,000, 1,500, 2,000, 3,000 and 4,000 and the StaticLoop translation units at 14 lengths from 2 to 19,902 operations, three compiles each, with the wall time, the peak memory (MiB), the nvcc phases and the cubin size of every compile. Median of three (spread 0.2 to 0.9 % at the lengths the paper quotes): N = 1 2.57 s, N = 1,000 22.3 s, N = 2,000 95.2 s, N = 3,000 262.4 s, N = 4,000 573 s (13,429 to 13,433 MiB = 13.1 GiB; cicc 425 s, host g++ 134 s, ptxas 11.4 s; cubin 197,023,392 bytes); StaticLoop 3.74 s at 2 operations, 10.09 s at 10,002, 31.5 s at 19,902 (1,073 MiB). These values replace the compile times of the sweeps above, which were measured while other compile jobs ran on the machine (the section before this one shows by how much); the code, the cubin sizes and the memory are the same. For the paper, the distinct-operations values are replaced in turn by the repeat at FKL 9e20bd4e (`repeat-pr423-9e20bd4e/`, next section); the StaticLoop values exist only in this set. The figures drawn from this set are `figures/compiletime_single_r2_c8fcbe8.*` and `figures/compiletime_distinct_only_r2_c8fcbe8.*`, the latter with the distinct-operations series only (no StaticLoop series); the old `compiletime_single_r2.*` is unchanged. Everything, the comparison with the values the paper quoted before and the load of the window is in `repeat-c8fcbe8/README.md`.
