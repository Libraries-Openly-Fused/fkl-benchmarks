# Same-day control of the compile time at N = 2,000: FKL c8fcbe8 and the head of PR #423 (9e20bd4e) alternating, 2026-11-06

Why: the controlled repeat at the PR #423 head (`../repeat-pr423-9e20bd4e/`, today 19:20 to 20:12) compiled 1.1 to 1.6 % slower than the repeat at c8fcbe8 (`../repeat-c8fcbe8/`, 2026-11-02) from N = 1,500 on, beyond the run-to-run spread; two things differed between those windows, the library tree and the state of the machine (restarted in between, other memory use). This control compiles the same translation unit with both trees in the same window, alternating, so that only the tree differs between neighbouring compiles. Approved by the coordinator (start 20:45:00, latest end 21:00).

## Conditions
- One window, 2026-11-06 20:45:00 to 20:55:02 by the machine's clock (the set ended 20:54:58); one compile at a time, nothing else of mine running and the other agents asked to run nothing; compile only, no GPU program. Load before 0.00 0.02 0.18; in `load.log` (every 20 s) the compile core's pair of hardware threads was busy 50 % (median), the other cores of that CCD 0 %, the other CCD at most 10 %; above 3 % of a core only the compilers, the sweep's python and the Claude sessions (at most 6 %).
- Trees: c8fcbe8 = the pin `external/fkl` of this repository (`external/fkl/include`); the head = `scratch/pr423/fkl-head` (`9e20bd4e5286be70fbeb0f79a19b96f00c81a06f`), both without local changes (`environment-before.txt`). Each compile's CSV header names its tree (`# fkl:`; for the head with the line `fkl tree (FKLB_FKL_TREE, ...)`).
- The translation unit: the distinct-operations chain (variant A of `fkl-self/compiletime/gen_chain.py`) at N = 2,000, generated by `scripts/e3_sweep.py` with the same text for both trees (`tu-sha256.txt`: one hash at N = 2,000, `b369bef9...`, the same as in both repeats; one at N = 1). The flags, core and tools of both repeats: core 8, `nvcc --threads 1 -O3 -DNDEBUG -std=c++17 --generate-code=arch=compute_89,code=[compute_89,sm_89] -ftemplate-depth=1000 -lineinfo --resource-usage`, CUDA 13.4.3 (nvcc 13.4.92), g++ 15.2.0; the python parents on cores 4-7,20-23, the load logger on core 5.
- Order (`window-script.sh`, `window-console.txt`): one warm-up compile at N = 1 per tree (`warmup_*.csv`, not used), then three pairs at N = 2,000 with the order swapped between pairs: (c8fcbe8, head), (head, c8fcbe8), (c8fcbe8, head); one CSV per compile, `pair<p>_<k>_<tree>.csv`, and its `nvcc --time` file in `nvcc-time/`.

**Reading.** At N = 2,000 the head compiles 1.12 % slower than c8fcbe8 in the same window (median against median; +1.19 % as the median of the paired differences), more than the spread of 0.61 % and under the 5 % flag; the head is slower in all three pairs, in both orders (+0.31 to +1.44 %). Between alternating compiles only the library tree differs, so this difference comes with the tree. It is smaller than the +1.59 % between the two repeats: c8fcbe8 compiles 0.37 % slower today than on 2026-11-02 (95.528 against 95.177 s), while the head gives the same today in both windows (96.599 here, 96.686 in the repeat: -0.09 %); that part of the repeats' difference is not the library. The time grows in cicc (+1.24 %), the host compiler (+0.81 %) and the front end (+0.58 %), not in ptxas; the peak memory is 19 MiB larger (+0.47 %). What in the tree makes the difference (the chain check of the four executors is what PR #423 adds) is not measured here.
