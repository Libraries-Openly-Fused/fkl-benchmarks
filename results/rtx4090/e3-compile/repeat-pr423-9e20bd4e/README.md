# E3 controlled compile repeat at the head of FKL PR #423 (9e20bd4e), 2026-11-06, against the repeat at c8fcbe8 (2026-11-02)

One window (2026-11-06, 19:20:00 to 20:12:02 by the machine's clock; the set was done at 20:11:51), approved by the coordinator; one compile at a time, nothing else of mine running and the other agents asked to run nothing on the machine (compile only: no GPU program ran). It is the set of `../repeat-c8fcbe8/` without its StaticLoop part, compiled against the library as it is at the head of FusedKernelLibrary PR #423 (the chain check of the executors; `../../fkl-pr423-check/README.md`). PR #423 was merged into LTS-C++17 on 2026-11-06 as `7b2deb6660921106e524a12cd5fca376feb0d544`, after #426; the merged tree differs from 9e20bd4e only in `.github/workflows/cmake-linux-rocm-amd64.yml`, one line that #426 removed; `include/`, `tests/` and `utests/` are the same tree objects, so these results apply unchanged to the merged commit.

## Conditions
- Library: the head of PR #423, `9e20bd4e5286be70fbeb0f79a19b96f00c81a06f`, a clone in `scratch/pr423/fkl-head` (detached, no local changes: `environment-before.txt`), given to the sweep as `--include .../fkl-head/include`. The pin of this repository (`external/fkl` at c8fcbe8) was not used. - Toolchain and machine as in `../repeat-c8fcbe8/`: CUDA 13.4.3, nvcc 13.4.92, g++ 15.2.0; Ryzen 9 5950X, Ubuntu 26.04.1, kernel 7.0.0-38; scaling governor `performance`, boost on.
- Every compile: ONE core (core 8, the second CCD), `nvcc --threads 1 -O3 -DNDEBUG -std=c++17 --generate-code=arch=compute_89,code=[compute_89,sm_89] -ftemplate-depth=1000 -lineinfo --resource-usage` (the flags of `scripts/e3_sweep.py`, unchanged); GNU time for the wall, user and system time and the peak resident memory; the phase times from nvcc's `--time` file. - **The translation units are the same files as in the c8fcbe8 repeat**: the sha256 of the eight generated `.cu` files (`tu-sha256.txt` of both folders) are equal at every N. Only the library tree differs, and the state of the machine (below).
- What differs in the state of the machine between the two windows (`environment-before.txt` of both): the machine was restarted in between (up 15 days on 2026-11-02, 3 days today); memory at the start (`free -m`): 48.5 GiB free and 11.5 GiB in shared memory (`/tmp`, where nvcc writes its temporaries, is a RAM disk) then, 100.3 GiB free and 0.2 GiB shared now; the one reading of the frequency of core 8 at the start was 4.01 GHz then and 4.40 GHz now. During both windows the load log is alike: the compile core's pair of hardware threads busy 50 % (median), the other cores of that CCD at most 1 %, the other CCD at most 10 %; above 3 % of a core only the compilers, the sweep's python, the Claude sessions (at most 7 %) and the desktop's file indexer (at most 4 %).

The c8fcbe8 repeat compiled N = 1, 1,000, 2,000, 3,000, 4,000 first and N = 100, 500, 1,500 at the end of its window, after its StaticLoop set.
- Units: the columns `*_mb` are MiB (GNU time reports KiB and the sweep divides by 1024); cubin sizes in bytes.

- Phases (medians): the front end `cudafe++` is longer at every N (+1.4 to +2.4 %, 0.012 to 0.021 s; more than the spread at every N except N = 100); `cicc` +1.4 to +1.8 % from N = 1,500 on (N = 4,000: 425.1 -> 432.5 s); `ptxas` -1.7 % at N = 3,000 and -2.4 % at 4,000 (11.39 -> 11.12 s); the host compiler -1.1 % at N = 4,000 (134.3 -> 132.8 s) and +0.7 to +1.1 % at N = 1,000 to 2,000. - **The generated code is the same**: registers, spill stores and loads, stack, constant bank 0, SASS instructions and .text bytes are equal at every N (`e3_repeat_vs_c8fcbe8.md`: 63 of the 64 code and size quantities equal). The one difference is the cubin size at N = 500: 3,643,552 -> 3,643,424 bytes (-128). Its sections that differ in size (`readelf -S` of the two cubins): `.debug_line` 37,224 -> 37,194 bytes, `.debug_str` +3, `.nv_debug_ptx_txt` +1, `.strtab` +1; the code sections are equal. These are the line information of `-lineinfo` and its strings; the path of the include directory and the line numbers of the library headers differ between the two trees. At the other lengths the cubin sizes are equal (the cubin sizes the paper quotes, N = 1,000 and 4,000, are unchanged).
- Printed values: the paper gives memory in GiB = MiB / 1024 (the unit fixed with PR #14): the peak memory at N = 4,000 is 13,432 MiB = 13.12 GiB at c8fcbe8 and 13,465 MiB = 13.15 GiB at the head, 13.1 GiB with one decimal in both. Which values the text prints today is the coordinator's and the paper agent's list; I have not checked it against the current paper.

**Cause: from this repeat alone, not determined.** Two things differ between the windows and this repeat does not separate them: the library (the head adds the chain check of the executors, `chain_check.h`, 213 lines, and its use in the four executors), and the state of the machine (restart, memory, order of the lengths). No compile at c8fcbe8 was made in this window. **Same-day control, done afterwards (20:45 to 20:55, `../control-n2000-c8fcbe8-vs-9e20bd4e/`): at N = 2,000, c8fcbe8 and the head alternating in three pairs, the head is +1.12 % slower (paired +1.44 / +0.31 / +1.19 %), beyond the spread of 0.61 %: at that length the difference comes with the library tree, and it is about 0.4 % smaller than between the two repeats (c8fcbe8 compiles 0.37 % slower today than on 2026-11-02).** The other lengths were not controlled. GPU- or host-bound: host (compile).
