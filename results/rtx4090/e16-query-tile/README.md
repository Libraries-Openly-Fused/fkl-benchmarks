# E16 query-tile experiment (RTX 4090, 2026-11-04 12:20:00 to 12:21:57)

Program `fkl-self/attention/e16_query_tile.cu` (origin/main 5023053; the decision rule is in its header comment and was pushed before the first run), analysis `scripts/e16_query_tile_analyse.py`. One window, whole machine quiet except the desktop session, RTX 4090 (nvidia-smi index 1), cores 0-3,16-19; three runs one after the other (E16_ROTATE 0, 1, 2, 38 to 39 s each), D = 128, non-causal, S = 512 .. 8192, BH = max(4, 262,144 / S), 10 variants, the order rotated per configuration and run; the first run is THE run, no row was dropped (50 rows per run). `run{0,1,2}/e16_query_tile.csv` (times with t_start_ms / t_end_ms per row, tile and kernel facts), `e16_query_tile_derived.csv/.md` (the rule applied), `window-console.txt`, `load.log`, `binary-sha256.txt`.

**BLOCK_KV.** The library's quantised (int8) schedule uses BLOCK_KV = 32; its default raw bf16 kernel uses BLOCK_KV = 64 (`raw_default`, reported only as the E16 control, 254 registers). The excess of the int8 kernel is therefore always taken against the raw kernel with the same BLOCK_Q, BLOCK_KV = 32 and the same warps (`raw_bq*_kv32_*`), never against `raw_default`.
**timing_only.** The `int8nodq_*` rows are TIMING ONLY (CSV column `timing_only` = 1): the output is wrong, their error columns mean nothing, and they are never a result. They come from a patched private copy of the library header (`fkl-self/attention/nodq/`, the diff next to it; the library is unchanged; the 14 kernels that exist unpatched have identical SASS): `dequantTile` REMOVES the int-to-float conversion, the multiply by the scale and the float-to-bf16 rounding and KEEPS the cp.async copies of the raw bytes, the staging area and the shared-memory pass, the barriers, the scale loads (kept alive with an empty asm volatile) and the same 16-byte shared-memory store. Their difference to the int8 kernel is the arithmetic only.

## Result (rule fixed before the run; ratio = excess(128) / excess(64), excess = int8 - raw at the same BQ, BKV = 32; median of the three runs, the three runs agree to 0.01 in the ratio)
| S | excess BQ64 (ms) | excess BQ128 (ms) | ratio | reading | share of the conversion, BQ64 / BQ128 |
|---:|---:|---:|---:|---|---|
| 512 | 0.145 | 0.084 | 0.57 | (rule applies from 2048) | 0.61 / 0.51 |
| 1024 | 0.241 | 0.136 | 0.57 | (rule applies from 2048) | 0.54 / 0.46 |
| 2048 | 0.496 | 0.240 | **0.48** | proportional to the number of query tiles | 0.44 / 0.46 |
| 4096 | 0.968 | 0.455 | **0.47** | proportional | 0.40 / 0.47 |
| 8192 | 2.025 | 0.886 | **0.44** | proportional | 0.33 / 0.48 |

int8 against bf16 at the same tiles: BQ64 +26.8 % (S = 2048) and +28.8 % (8192); BQ128 +13.2 % and +12.6 %. A ratio near 0.5 shows a cost that is repeated per query tile; it does not by itself show that it is the conversion. The share of the conversion, (int8 - int8nodq) / (int8 - raw), is the arithmetic only: about 0.33 to 0.61 of the excess at BQ64 (falling with S) and 0.46 to 0.51 at BQ128; the rest of the excess is what `int8nodq` keeps (the shared-memory pass, barriers, loads); it also halves with the query tiles (ratio 0.47 at S = 2048, 0.34 at S = 8192 for nodq - raw). So both parts, the conversion and the rest of the quantised schedule, fall with the number of query tiles; the conversion is about a third to a half of the extra time and not all of it.

## What does not follow the rule: BQ32 (2 warps)
`int8_bq32_w2` is 2.4 times slower than `int8_bq64_w4` (5.62 against 2.34 ms at S = 2048) and `raw_bq32_kv32_w2` is 11 % slower than raw BQ64 (2.05 against 1.85): at 2 warps with 48 KB of shared memory per block (int8) only 2 blocks of 2 warps fit per SM (occupancy 8.3 % against 16.7 %), so the BQ32 point confounds the tile with the occupancy and is not interpreted by the ratio rule (excess BQ64 / BQ32 = 0.14 at S = 2048, far from 0.5). Kernel facts at S = 2048 (registers, local memory B, dynamic shared memory B, blocks per SM): raw_bq64_kv32_w4 171, 0, 24,576, 2; raw_bq128_kv32_w4 255, 56, 32,768, 2; int8_bq64_w4 174, 0, 49,152, 2; int8_bq128_w4 255, 40, 49,152, 2; int8nodq: 174, 255 (40 B local) as int8; raw_default 254, 0, 49,152, 2. The BQ128 kernels use 255 registers and spill 56 and 40 bytes (raw and int8): both are affected alike. DEEP_Q_SMEM is a constant false in the library and DUAL_Q_SMEM needs FK_FA_DUAL_Q (default 0) and the raw schedule: neither is active for any variant.
