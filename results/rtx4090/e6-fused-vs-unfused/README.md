# E6 (reduced set): fused against kernel-per-op, -fmad, special values, aliasing (RTX 4090, 2026-11-04)

Program `fkl-self/numerics/e6_fused_vs_unfused.cu`, specification `fkl-self/numerics/README_e6_fused_vs_unfused.md` (written and pushed before the program and before any result: c04c2db and the dated note 91dfcdd). Two windows, both with the whole machine quiet except the desktop session, RTX 4090 (nvidia-smi index 1), cores 0-3,16-19: **run 1** 2026-11-04 11:45:00 to 11:45:06 (this folder, THE run), **run 2** 11:56:00 to 11:56:06 (`../e6-fused-vs-unfused-run2/`: the same program plus five new CSV columns, requested after run 1; the first run's files were not touched). Run 2 reproduces run 1 bit for bit: **160 of 160 raw bit-pattern files identical** (`../e6-fused-vs-unfused-run2/e6_determinism_run1_vs_run2.csv`), so the counts below hold for both. Built twice from the same source: `build/rtx4090` (-fmad on, the nvcc default) and `build/rtx4090-fmad-off` (`-fmad=false`); OpenCV and NPP off in both, host references `-ffp-contract=off`; binaries' sha256 in `binary-sha256.txt` (run 1) and the run 2 folder. The raw outputs (bit patterns, 131 MB per build and run) are in `results/cuda13.4/e6-raw` and `e6-raw-run2`, outside the repository.

## What was run (counts)
- **P1**: float 480 x 270 = 129,600 elements per seed (reduced from 1920 x 1080 only to keep the raw files small), uniform [0.5, 2], 5 seeds, chains of 1, 10, 100 and 1,000 x (Mul 0.999f, Add 0.003f) (fixed point 3.0; every value stays in [0.5, 3]: finite and normal; the 1,000-pair chain does NOT collapse: 0.0 % of the elements share one value, about 124,200 of 129,600 values are distinct). Fused: one StaticLoop kernel. Per-op: 2 x pairs launches, ping-pong between two float `Ptr2D` buffers (every intermediate is a float in global memory).
- **P2**: 50 crops of 60 x 120 of a 3840 x 2160 uchar3 noise image -> 64 x 128 (six on the edge: four corners, one ending on the last row, one on the last column; 44 random interior), **P3**: one 1920 x 1080 image -> 224 x 224 (ROI = the whole image; border = first/last output row and column); both in both sampling conventions (ASYMMETRIC, HALF_PIXEL), 5 seeds. Chain: Resize (bilinear) -> VectorReorder<float3,2,1,0> -> Mul 0.3 -> Sub (1, 4, 3.2) -> Div (3.2, 0.6, 11.8) -> TensorSplit. Fused: one kernel (the E4a code, BatchRead of the crop ROIs). Per-op: per crop six launches with the intermediates: (1) resize of the crop ROI, uchar3 -> float3 `Ptr2D` A; (2) reorder A -> float3 `Ptr2D` B; (3) Mul B -> A; (4) Sub A -> B; (5) Div B -> A; (6) TensorSplit of A into a float tensor of that crop, copied into the batch tensor. Every intermediate is float3 in global memory, so the per-op path rounds to fp32 after every operation by construction.
- **Launch counts are by construction of the code, not counted by a profiler:** P1 per-op 2,222 launches per seed (11,110 for 5 seeds) + 20 fused; P2 300 per-op launches per case, 3,000 for the 10 cases (2 conventions x 5 seeds), + 10 fused; P3 6 per case, 60, + 10 fused. 80 raw files per build (40 P1: 4 lengths x 5 seeds x 2 paths; 40 P2/P3: 2 pipelines x 2 conventions x 5 seeds x 2 paths).
- Special values: 47 inputs; Add, Sub, Mul, Div x 7 operands (329 cases each), Mul-add 47, Normalize 47, Cast 235, SaturateCast 235, RGB2Gray 141, VectorReorder 141, Resize 512 (2 conventions x 256 output pixels); 2,565 scored cases + 109 Cast cases not scored (undefined behaviour in C++). Every case is a row of `<tag>/e6_special_values_<tag>.csv`.
- Aliasing: element-wise chain (1,000 Mul/Add pairs, 2,073,600 floats) in place against out of place, once; resize-to-half gather in place against out of place, three runs.

With -fmad off fused and per-op are **bit-identical in every case** (all pipelines and lengths, interior and border, 5 seeds); with -fmad on they differ only through the contraction of a multiply and the following add or subtract into one fma, which the per-op path cannot do across launches. The border (the six edge crops of P2, the clamped first/last row and column of P3) behaves like the interior: the same fraction of differing elements and no larger error.

## Result 2: against the fp64 reference (the double chain rounded once to float; ULP of the integer distance of the bit patterns)
**Contraction here improves the agreement with the double reference, it does not worsen it.** P1 with 1 pair, -fmad on: fused is identical to the fp64 result in all 648,000 elements (one fma = one rounding), per-op differs in 151,398 (1 ULP); with 1,000 pairs fused is within 22 ULP, per-op within 77 ULP (and -fmad off fused 77). P2: fused with -fmad on within **1 ULP** of fp64 at every element; with -fmad off up to 1,820 ULP (ASYM) and 2,591 (HALF), at elements whose result is close to zero. The new columns of run 2 (`../e6-fused-vs-unfused-run2/e6_new_columns.csv`) say what these ULP numbers mean:

| fused vs fp64 | max ULP (|output| at that element) | max abs error | max abs error / max |output| | elements below 1e-3 (cancelling zone) | max ULP outside the zone |
|---|---|---|---|---|---|
| P1 1,000 pairs, on / off | 22 (2.3) / 77 (2.32) | 5.3e-6 / 1.8e-5 | 2.0e-6 / 7.0e-6 | 0 | 22 / 77 |
| P2 ASYM, on / off (interior) | 1 (11.9) / 1,820 (1.3e-3) | 7.6e-6 / 7.6e-6 | 6.3e-8 / 6.3e-8 | 28 of 5.4 M | 1 / 1,820 |
| P2 HALF, on / off (interior) | 1 (11.5) / 2,591 (5.8e-5) | 7.6e-6 / 7.6e-6 | 6.3e-8 / 6.3e-8 | 39 of 5.4 M | 1 / 1,139 |
| P3 ASYM, on / off (interior; border) | 2.47e6 (3.0e-4); 6.6e6 (1.1e-3) / 2.47e6; 6.6e6 | 0.0164; 0.0122 | 1.4e-4; 1.0e-4 | 4 of 739,260; 0 | 1.1e6; 6.6e6 |
| P3 HALF, on / off (interior; border) | 5.1e6 (1.3e-2); 1.9e5 (2.7e-3) / same | 0.0165; 0.0188 | 1.4e-4; 1.7e-4 | 5; 0 | 5.1e6; 1.9e5 |

What it shows: (i) For P1 and P2 the ULP maxima are where they should be: P2's absolute error is 7.6e-6 (one float ULP of the largest outputs) and 6.3e-8 of the largest output with -fmad on and off alike; the 1,820 and 2,591 ULP at -fmad off sit at output values of 1e-3 to 1e-5, where the chain (x*0.3 - 1)/3.2 cancels to near zero and an absolute error of one ULP of the largest values is thousands of ULP of the result: ULP at a zero crossing is not an accuracy measure, the absolute error normalised by the largest output is (6.3e-8, about half a float ULP of the maximum). The cancelling zone threshold of 1e-3 contains few elements (28 of 5.4 M) and the worst element is just outside it, so 'ULP outside the zone' does not drop. (ii) For **P3 the explanation by cancellation is not enough**: the absolute error against fp64 is 0.012 to 0.019, about 1e-4 of the largest output, 1,000 times a float rounding error, in both builds. It is a real difference between the float resize and the double evaluation for the 8.57-fold downscale (consistent with a float32 source coordinate x * 8.571 near 1,900, whose spacing 1.2e-4 pixel times pixel differences of about 85 gives about 1e-2 in value; this is an explanation consistent with the numbers, not shown by this run). It is not caused by fusing (fused and per-op agree with -fmad off) and it is the same size at the border and in the interior. P3's -fmad on/off difference (max 0.0064 absolute at an output of 0.46 for HALF seed 0) has the same scale.

## Result 3: special values (`<tag>/e6_special_values_<tag>.csv`, summary `..._summary_<tag>.csv`)
2,439 of 2,565 scored cases give the specified result with -fmad on, 2,440 with -fmad off. All exceptions, in two kinds (class (a): library or hardware behaviour differing from the pre-registered expectation; none of class (b) specification fault or (c) program fault):
1. **RGB2Gray with a float output, 125 of 141 cases in both builds**: the gray value is rounded to an integer. `color_conversion.h` tests `std::is_unsigned_v<OutputType>` then `std::is_signed_v<OutputType>`; `std::is_signed_v<float>` is true, so a float output takes the integer branch (`__float2int_rn` on the device) and the floating-point branch is never reached. Verified on all 141 rows of both builds: observed = float(rint(expected)), NaN -> 0, saturating (+Inf -> 2147483648). Example: (0.5, 0.5, 0.5) gives 0, not 0.5. No measured program of this repository uses RGB2Gray (grep of common, fkl-self, opencv-cuda, npp, scripts); cvGPUSpeedup's own colour tests use integer outputs.
2. **Normalize (x * 0.3 - 1) / 3.2, 1 case with -fmad on only**: x = 2.5 gives 0xbd9fffff instead of 0xbda00000: Mul and Sub contracted into one fma; with -fmad off it passes.
Not exceptions but results: all Add/Sub/Mul/Div (1,316 per build, including zero signs, Inf rules, denormals, overflow), Mul-add, SaturateCast (235: NaN -> 0, ties to even, saturation), VectorReorder (141, bits unchanged) and Resize with planted NaN/Inf/-Inf/0 in both conventions (512) pass every case. The device returns the canonical NaN 0x7fffffff whatever the payload and sign of the input in 352 NaN-producing cases per build (criterion 'is a NaN'; `payload_differs` column). **Cast** (static_cast), not scored, observed: NaN -> 0 for all types; +Inf -> 255 (uchar), -1 (schar), -1 (short), 65535 (ushort), 2147483647 (int); -Inf -> 0 (uchar, schar, short, ushort), -2147483648 (int); 2^31 -> 0, -1, -1, 0, 2147483647; 2^32 -> 255, -1, -1, 65535, 2147483647.

## Result 4: aliasing
Element-wise chain, input = output pointer: **0 of 2,073,600 elements differ** from the out-of-place result, bitwise, in both builds. Resize-to-half gather in place (518,400 outputs), three runs: -fmad on 1,952, 1,664, 2,368 elements differ; -fmad off 2,192, 2,352, 1,616 (it varies from run to run: a race). Run 2: the element-wise chain again 0 differing in both builds; the gather 2,528, 2,160, 2,336 (-fmad on) and 2,112, 2,192, 1,920 (-fmad off) differing elements: not reproducible between runs, as a race is not.

## Dated notes
- **2026-11-04, CPU-only check of P3 against fp64 (`p3_host_float_check.txt`, program `fkl-self/numerics/e6_p3_host_float.cpp`, no GPU, compiled with `-ffp-contract=off`).** The P3 inputs of seeds 1100 to 1104 were regenerated from the same random stream, and the same resize chain was written on the host in float32 with the formulas of the library source (scale = float(1.0 / (dst / src)) computed in double, source coordinate x * scale in float (HALF_PIXEL: max((x + 0.5f) * scale - 0.5f, 0)), weights (x2 - sx) * (y2 - sy) etc. in float, the four products summed left to right, then reorder, Mul, Sub, Div in float). Result, 5 seeds x 2 conventions: (1) the host float32 result differs from the double evaluation by 0.0138 to 0.0188 absolute, 1.1e-4 to 1.6e-4 of the largest output: the same error as the device; (2) the host float32 result is **bit-identical to the device output built with -fmad off in all 150,528 elements of every seed and both conventions** (max abs 0, max ULP 0); against the device built with -fmad on it agrees in about 75 % of the elements and differs by at most 2.3e-5 (ASYMMETRIC, up to 285 ULP) and 0.0070 (HALF_PIXEL, up to 7,190 ULP) in absolute value, i.e. the contraction of the coordinate arithmetic; (3) with the source coordinates and weights computed in double and only the pixel sum and the chain in float, the maximum absolute error against the double drops to 9.1e-6, 7.5e-8 of the largest output (one float ULP of the largest values), the same level as P2. Conclusion: the 1e-4 of P3 against fp64 is the precision of float32 source coordinates and weights in the formulas of the library (positions near 1,900 pixels have a spacing of 1.2e-4 pixel; times pixel differences of about 85 gives about 1e-2 in the pixel value); it is inherent to evaluating that formula in float32, it is the same on the host and on the device, it does not depend on fusing, and it is not a defect of the device code. It was not tested what a different formulation (for example coordinates relative to the output centre, or double coordinates) would give in speed.
