## E9, the four facts in the order of the paper (details in `e9_summary.md`)
**(a) Launches.** Each of M1, M2, R1, R2 is ONE kernel per call: kernel nodes of one captured call = 1 in all three runs. nsys, one call of each of the four variants and of the two listings in a profiler range: 6 kernel launches (5 kernel types; the long listing has the type of M1, so that type is launched twice).
**(b) Bit identity.** `compare()` in `npp/e9_cross_library.cu`: `memcmp` of the 4-byte bit pattern of every output float (1,228,800 per comparison: 50 crops x 3 channels x 64 x 128), plus the NaN count of both outputs; the output is pre-filled with the NaN pattern 0xff so an unwritten element would show. 3 runs x 3 seeds = 9 rows per comparison (`e9_agreement.csv` of each run): **M1 with R1, M2 with R2, the long listing with M1 and the short listing with M1: bit-identical in all 9 rows, NaN count 0.** R1 with R2 and M1 with M2 differ (1,227,858 to 1,227,896 of 1,228,800 elements, max abs 1.204): the cvGS resize samples asymmetrically, the FastNPP resize at the pixel centre since #45 (the convention difference, as predicted).
**(c) Time per call, mixed against the single-library kernel that shares its resize** (3 runs, rotated order; ratio formed per run; GPU time from a CUDA graph of 100 calls, GPU-bound, flag 3 %; a call is about 6 microseconds):
| pair | ratio run 0 (THE run) / run 1 / run 2 | median | spread over runs | beyond the flag |
|---|---|---:|---:|---|
| M1 / R1 | 1.0398 / 1.0269 / 1.0255 | +2.7 % | 1.4 points | run 0 (+4.0 %) |
| M2 / R2 | 0.9858 / 0.9822 / 0.9673 | -1.8 % | 1.8 points | run 2 (-3.3 %) |
GPU time per call, median of the 3 runs: M1 5.94, R1 5.74, M2 5.95, R2 6.06 microseconds (block range inside a run up to 2.4 %). The launch loop (plain back-to-back launches, host-bound, flag 5 %): M1 / R1 +2.4 %, M2 / R2 -3.1 %, no run beyond the flag. **The prediction "M within the spread of R" is NOT met for M1 / R1** (+2.7 % against a spread of 1.4 points; run 0 above the 3 % flag); for M2 / R2 the difference (-1.8 %) equals the spread. The sign follows one operation: the kernels with FastNPP's swap (`VectorReorderRT`, M1 and R2) are 1.8 to 2.7 % slower than the one with the compile-time swap (R1, M2) of the same pair; the comparison of the demangled kernel types shows the swap is the ONLY operation in which a mixed kernel differs from its reference (SubC / DivC and subtract / divide are the same types; this corrects the clause in the first version of the header note). In both pairs the kernel with the run-time swap is the slower one in all three runs (M1 over R1: +4.0, +2.7, +2.6 %; R2 over M2: +1.4, +1.8, +3.4 %). This is consistent with the swap explaining the difference (and with the instruction mix, below); it is not isolated (no control kernel was run). A position effect of about 1 % is visible in the rotation (R1: 5.79 microseconds at the first position of run 2 against 5.72 and 5.74 at later positions; M2 and R2 are lower at later positions too); it may be part of the +4.0 % of run 0 (M1 first, R1 third); not isolated.
**(d) Registers and SASS lines** (cuobjdump, sm_89, final binary; stack, shared and local memory 0 in all): M1 34 / 552, R1 32 / 544, M2 33 / 552, R2 32 / 568; the short-listing kernel 34 / 552. Compared with the numbers before the window: M1, R1 and the short listing unchanged; M2 544 -> 552 and R2 560 -> 568 lines (the half-pixel coordinate of #45), registers unchanged. The kernels with the run-time swap have about 5 more FSEL, 6 more ISETP and 6 more IMAD than the one with the compile-time swap (M1 against R1: FSEL 20/15, ISETP 22/16, IMAD 34/28; R2 against M2: 22/17, 21/15, 35/29).

## Note 2026-11-06 (after the window): the printed short listing is the kernel that was timed
The short listing (`npp/e9_cross_library.cu`, `short_listing::Gamma` at lines 70-76 and the call at lines 254-261) is a distinct C++ instantiation (its own `Gamma` type, so its own kernel symbol) and was NOT timed on its own: the timed variants are M1, M2, R1, R2 (the ratios of the paper are M1 against R1). What backs the statement is the identity of the code: `scripts/e9_sass_hash.py` on the binary of the window (sha256 32cdead6..., `binary-sha256.txt`) hashes the `cuobjdump -arch sm_89 -sass` instruction lines of every `launchTransformDPP_Kernel` (addresses removed): M1 and the short-listing kernel have 552 instruction lines each, the same instruction text (hash 5fbba92686a1f3b0) and the same machine code including the encoding and control words (hash 12c9c342af78a6ff), so the code that ran as M1 is the code the short listing compiles to; its output is also bit-identical to M1 in 9 of 9 comparisons (`M1shortlisting_vs_M1`). The same check by the coordinator, with another normalisation of the text, gives the same equality (its hash, 42ccf12f6ba263c0, is of that normalisation). Result of the script: `sass-hashes.txt` (R1 544 lines, M2 552, R2 568 for comparison).
