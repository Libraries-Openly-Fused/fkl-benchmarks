# E9 cross-library kernel (cvGPUSpeedup + FastNPP + a user operation in one `fk::executeOperations`)

Program `e9_cross_library.cu` (target `e9_cross_library_cu`); design, predictions and what the demonstration does and does not show are in its header comment. Four kernels: M1, M2 (mixed), R1 (all cvGS), R2 (all FastNPP), the same user gamma in all.

- **Listing:** lines 294-301 of `e9_cross_library.cu` (the call in the lambda `listing`), a comment on each line names the origin of the operation.
- **Prediction (2) was false** (dated note in the header): M and R differ by 8 to 16 SASS lines (M1 34 registers / 552 lines, R1 32 / 544, M2 33 / 544, R2 32 / 560; stack, shared, local 0) because the swap is a different FKL type in the two wrappers (FastNPP: `VectorReorderRT`, run-time index vector; cvGS `cvtColor` RGB2BGR: `VectorReorder<float3, 2, 1, 0>`, compile-time). *Correction of 2026-11-06, after the window:* the first version of this sentence also named SubC / DivC against subtract / divide; the comparison of the demangled kernel types shows that these are the SAME FKL types, and the swap is the only differing operation between a mixed kernel and its single-library reference. The SASS comparison is a size comparison, not an identity test, and the time comparison M against R contains that difference as well.
- **Since the cleanup of 2026-11-07** (line numbers above are of the cleaned program; the two printed blocks are byte-identical to the earlier ones):
  - each library reads its own copy of the frame: the cvGPUSpeedup operations read a `GpuMat` uploaded from the noise bytes, and their crops are ROIs of it; FastNPP reads a `cudaMallocPitch` image of the same bytes, and its descriptors use the NPP pointer idiom;
  - every call of a variant builds its batch (the ROIs or the descriptor and ROI arrays) and its operations, because the crop locations may change on every image. `launch_ms` therefore includes that host work; `graph_ms` cannot, since a graph replays only the kernel;
  - R1 runs on cvGPUSpeedup's own executor (`cvGS::executeOperations` on an OpenCV stream wrapping the plain stream) and writes a continuous `GpuMat`. M2 and R2 write dense `cudaMalloc` tensors through plane pointers. The `NppStreamContext` is filled field by field;
  - the kernels are unchanged (`scripts/e9_sass_hash.py`: the same instruction-line counts and text and code hashes for M1, the short listing, R1, M2 and R2). R1's kernel name now carries cvGPUSpeedup's default thread-fusion template arguments (`TF::ENABLED`), and its machine code is the same.
- **Friction in the first draft** (an ambiguous `Gamma::build`) was a mistake of the program, not a finding about the libraries.
- **Short listing (for the paper, compiled and compared):** user op `short_listing::Gamma`, lines 67-73 (7 lines, block 65-75); call, lines 307-314 (8 lines, in the block 303-316); its output is compared with M1 in the window (`M1shortlisting_vs_M1`). Its kernel has 34 registers / 552 SASS lines, like M1.
- **The four facts of the window, in this order:** (a) each mixed kernel is ONE launch (kernel nodes of one call captured in a CUDA graph, `e9_timing.csv` column `kernels_per_call`; nsys as cross-check); (b) each mixed kernel's output is bit-identical to the single-library kernel that shares its resize (M1 with R1, M2 with R2): function `compare()` in `e9_cross_library.cu` (memcmp of the 4-byte bit pattern of every output float, plus the NaN count of both outputs; the output is pre-filled with the NaN pattern 0xff so an unwritten element shows), rows in `e9_agreement.csv`; (c) the time of each mixed kernel against its single-library kernel, 3 runs with rotated order, with the run-to-run spread (`e9_timing.csv`); (d) registers and SASS lines from the final binary of the window (compile-time values: 34 / 552 against 32 / 544, and 33 / 544 against 32 / 560; state if they changed). No unfused count is taken.
- Results (bit-exact check, kernel counts, times) come from the single window after FastNPP #45 is merged and the pin is moved; none exist yet.
